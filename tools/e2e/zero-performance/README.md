# Zero performance gate

`pnpm test:zero:performance` measures the complete registered query catalog and real browser navigation against its own local Supabase/Zero stack. It fails immediately on missing coverage, missing metrics, wrong results, slow-query warnings, or exceeded budgets. There is no grandfathered slow-query allowlist.

Requirements: the pinned Node/pnpm dependencies, Docker, Supabase's images, and Chromium (`pnpm exec playwright install chromium`). The command chooses unused ports in 55620–55819, generates a unique Supabase project ID, copies the working tree into `output/zero-performance/`, builds it in production mode, and always stops its own stack. It never resets or reuses the normal development project. Startup, build, connection establishment and replication readiness are recorded separately from query execution.

Commands:

```sh
pnpm test:zero:performance
pnpm test:zero:performance --baseline-ref origin/master
pnpm test:zero:performance --collect-all
pnpm zero:analyze --query users.current --case default
```

The default gate stops after the first violating measurement, as required for immediate CI failure. Registry reconciliation and the complete fixture preflight still run first. The partial report explicitly lists all expected keys; missing cases cannot produce a successful gate. Use `--collect-all` to continue past violations and inventory all slow queries. That survey enforces the same budgets and still exits unsuccessfully if any check fails.

The analyzer runs the same real materialization, server analysis and result assertions for a selected query. Its report is marked filtered and cannot satisfy the full CI gate. The case names are `default`, `search`, `backward`, `next-page`, `outgoing`, `sort-time`, `sort-engagement`, `sort-trending` `initial-grid` and `initial-grid-search`, where supported by the input schema.

The reviewed `cases.ts` inventories query names, statically typed and runtime-validated arguments, positive root tables/anchors and a revision plus explanation. `catalog.ts` reconciles it with the real registry; additions and deletions fail before execution. The authoring helper `catalog-generation.ts --write-catalog` is for initial/reviewed authoring only and is never run by CI. Inspect its changes rather than automatically replacing expectations.

Fixtures use live PostgreSQL metadata and real constraints/triggers to construct a minimal positive dependency graph. Nullable backlinks are inserted and restored without disabling constraints. Unsupported predicates, nonnullable cycles and fixture failures fail closed. A populated case must actually return its anchor. The SQL oracle independently executes the ZQL root predicate in PostgreSQL and compares complete authoritative root IDs; it does not claim to prove all product authorization policies by itself. The dedicated security scenarios separately assert expected allowed/denied results and subscribed revocation behavior. Existing access/integrity tests remain required.

For every case the suite measures an empty profile and a minimal positive profile. The minimal profile also runs as an unrelated authenticated user and as an anonymous viewer. Global/system queries may legitimately return the minimal actor records on the otherwise empty profile. Pagination variants verify the exclusive cursor boundary. Each measurement uses five fresh in-memory stores/client groups. Idle connection setup is prepared concurrently before activation; the five materializations and all analyzer runs remain sequential. All five fresh-client materializations finish before analysis begins. The first real view stays subscribed for three analyzer warmups and twenty measured runs. The join-plan export follows those measurements. A diagnostic timeout still fails the case; collect-all continues to attempt the remaining materializations. Older measurement protocols cannot serve as comparable acceptance baselines. JWTs are renewed during setup when needed, so long suites continue to exercise the intended authenticated identity. Normal client and server warning thresholds remain unchanged.

Budgets: total first authoritative result ≤1,000 ms, local initial materialization ≤50 ms, server analysis p95 ≤100 ms, and zero slow-query warnings. Fresh-client wall time includes subscription activation and server auth/query transformation; connection setup is excluded. Inspector timings must also be present. These are reproducible local budgets, not production network guarantees.

Warmups and the twenty timed analyzer runs use the public `joinPlans: false` option. The complete join trace is exported once afterwards with `joinPlans: true`, with its own `exportMs` diagnostic duration. Timed samples retain Zero's unmodified `elapsed` value, row work and warnings. Missing plans and slow-query warnings from the separate export still fail the measurement.

Reports contain JSON samples, root-case identities, SQLite/join plans, rows read/scanned/synced, browser navigation and failures. `api-timing.mjs` is loaded only into the sandbox server and records Supabase `getUser` fetch duration without tokens or request bodies. CI uploads reports and logs, not copied source trees, local databases or browser sessions.

The report format is `6`, with measurement protocol `zero-performance/v6`. Every fresh materialization correlates its public query ID and activation interval with one API request, its authentication/transform timings and AST size. Raw HTTP arrival/response records are retained; missing or ambiguous correlation fails. The validator reconstructs the correlation from those raw records. Response-to-authoritative time is a separate observed interval that overlaps server hydration, transfer and local processing; the phase times are never subtracted from budgets or added as if they were disjoint. Preloads have individual activation IDs and real start/completion/release timestamps. A pure preload does not create a local result view: its `preload.complete` is required within 1,000 ms; absent view materialization timings are expected. Materialized views always require a real Inspector client timing within 50 ms. Each view additionally records activation, authoritative completion and release. An already authoritative preloaded view may have no Inspector total hydration timing; its actual public-hook activation-to-completion duration is checked instead. Present Inspector totals are still checked. Missing completion or local timing fails; no duration is replaced with zero. Browser route readiness and painted content are recorded independently. Inspector exports occur after navigation timing and their own duration is reported.

Build caches and Nitro intermediate files are private to the sandbox, even when pinned dependencies are shared. Readiness checks require a resolved application stylesheet and verify that browser assets referenced by the server actually exist before measurements start. A build with missing styles cannot produce acceptance timings for the application layout.

Raw hook observations distinguish React render attempts from committed views. Suspense can abandon a render attempt before it creates a visible view; these attempts remain in diagnostics. Activation-to-authoritative-result checks apply to committed views, including views released before completion. Inspector checks still cover every active materialized query independently.

For a diagnostic Linux control from Windows, `node tools/e2e/zero-performance/run.mjs --query users.current --collect-all --zero-image IMAGE --output output/zero-performance/linux-control-new` can use a locally prepared Linux image. The runner verifies its exact pinned Node/Zero versions, every Zero JavaScript file and the complete required transitive dependency versions against the benchmark install before starting it. An identical Zero package alone is insufficient. This does not change Zero and does not replace the native Ubuntu CI control. Diagnostic `--layer fixtures`, `--layer security` and `--layer journeys` runs cannot satisfy the full gate.

If the installed dependency closure contains versions absent from the lockfile, the sandbox installs dependencies with `--frozen-lockfile --ignore-scripts` and rebuilds only the pinned Zero SQLite native binding. The same private install applies to a baseline with a different lockfile and can be requested explicitly with `--frozen-dependencies`. Existing development dependencies and the lockfile are left untouched; dependency setup time and rejected installed versions are reported separately.

`--profile-navigation` exports `navigation.cpuprofile` by replaying the six routes after all timed navigation samples. It does not instrument the acceptance samples. These runtime flags can also be passed to `pnpm test:zero:performance`; head, baseline and confirmations use the same runtime choices.

Adding `--linux-app` runs the same saved production server build in that verified image, using the isolated Supabase Docker network and explicitly published application ports. This separates Windows application-server overhead from the Linux Zero control. Image verification time and both server platforms are recorded separately. Windows build junctions are copied as real files into the private artifacts; authentication and replication use the same isolated services through container DNS. It preserves the same queries, result checks, analyzer samples and absolute budgets; it is not evidence that the Ubuntu CI job has run. Both containers carry the isolated project ownership label and are stopped by normal and interrupted-run cleanup.

On PRs, head and the base SHA run sequentially on the same runner. A >20% median increase AND >10 ms server / >100 ms total increase triggers a second comparison of the affected query cases, again on both revisions on that runner. Both complete first reports and the filtered confirmation reports are preserved; filtered runs cannot replace the initial full gate. Absolute budget failures remain comparable when telemetry and results are complete. Invalid telemetry is explicitly listed as excluded and still fails the gate. More read/scanned rows also require reconciliation. Only a higher case revision with a changed explanation can acknowledge intentional additional row work; it never relaxes absolute or timing regression budgets. The introduction PR can have a base without the benchmark; that bootstrap is explicitly reported and still enforces all absolute checks.

Each completed measurement is immediately appended to `measurements.ndjson`; `progress.json` records ongoing coverage and browser diagnostics. The final `report.json` and the query/navigation CSV tables are written on completion or failure. This preserves partial diagnostics without repeatedly rewriting the growing full report during timing runs.

Collection runs sequential workers of at most twenty query variants against the same isolated server stack, followed by separate security and browser workers. This bounds retention from thousands of fresh client instances without changing Zero, the number of samples, connection readiness, or any measured duration. Worker startup and elapsed wall time are recorded separately; all worker reports and partial NDJSON files remain available after crashes. The parent reconciles every expected case, retains full plan artifacts and reconstructs API correlation. A crash, missing worker case or interrupted collection remains a failure. Protocol v5 reports cannot replace v6 acceptance reports.

Failure artifacts remain in the output directory for diagnosis. Optimize based on the separated measurements; do not remove authorization predicates or relax budgets to make CI green.

Run existing database integrity contracts with `node tools/e2e/zero-performance/run.mjs --layer integrity --output output/zero-performance/integrity-new`. This diagnostic command creates its own Supabase project, overrides all supported database URL aliases with the verified private database, runs the complete Vitest database-integration project, saves `integrity.json` and `integrity.log`, and stops only its own stack. It creates no performance acceptance report and cannot satisfy the performance gate. Ordinary database test commands may default to the development database; use the isolated command for this optimization workflow.

Join traces are saved individually in plans/ with a SHA-256 digest, byte count and trace count in each measurement. The gate verifies every referenced export, one at a time. Missing or altered exports fail. This preserves the complete diagnostics without holding hundreds of megabytes of join traces in the runner heap.

Reports record the full independent security expectation manifest. Head reconciles it against the current business cases; a baseline must completely satisfy its own recorded cases, even when the head adds coverage. Missing cases, changed expectations, duplicates and incorrect results still fail. Public elections are asserted present while independently private roles remain absent, including after holder revocation.

The search grid uses its existing maximum of 48 rows from the first query, with one look-ahead row. Its preload uses the identical 49-row query and the catalog measures this initial-grid variant separately. Responsive layout no longer triggers successive 19/37/49 subscriptions; cursor and permalink paging still use the public adapter.

The public ZeroProvider initializer registers the authenticated initial route and core query demand before child effects mount. Search parameters and the selected message conversation use the same argument builders as their visible pages. The initializer joins the normal preload registry, retains started work until completion, and releases only its own reference afterwards. Its module-stable identity prevents navigation or session refresh from recreating the Zero client.
